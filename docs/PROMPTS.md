# 發給 AI 的提示詞結構

> 這份文件整理所有送給 AI 的請求。程式碼在 `src/narrator/prompt.ts`（敘事）、`src/narrator/judge.ts`（判定與生成）、`src/narrator/lore.ts`（世界書）、`src/narrator/promptConfig.ts`（文風與其他提示詞）、`src/narrator/compose.ts`（依設定組合）。玩家在首頁的「🧩 提示詞管理」（或遊戲中上方的「🧩 提示詞」頁籤）調整與預覽。
>
> **提示詞組**：可以同時存有好幾組提示詞（每一組有自己的文風、其他提示詞與世界書的修改），用最上方的「🧩 提示詞組」新增（從預設內容開始）、複製、改名、刪除（至少留一組）與切換。**隨時可以切換**，遊戲中也可以，下一次呼叫 AI 就用新的一組。存在 localStorage 的 `elondia.promptSets`；舊版的設定（`elondia.prompts`）第一次啟動時變成「預設」這一組。
>
> 上層：[GAME_DESIGN](GAME_DESIGN.md) 第 5 節。依賴：[RELATIONSHIP_MEMORY](RELATIONSHIP_MEMORY.md)（`<relationships>`、`<memories>`）、[ACTIONS](ACTIONS.md)（判定請求的內容）。被依賴：[PORTRAITS](PORTRAITS.md)（插圖提示詞預處理用的模型來源）。

## 0. AI 服務

玩家在「設定」自行輸入 API key，key 只存在瀏覽器的 localStorage，請求直接從瀏覽器送出（`src/narrator/providers.ts`）。支援四種格式，各家 SDK 用到時才載入：

| 格式 | SDK | 備註 |
|---|---|---|
| Anthropic（Claude） | `@anthropic-ai/sdk` | 預設 `claude-opus-5-5`；支援的模型自動開啟伺服器端拒絕備援（`fallbacks: "default"`） |
| OpenAI | `openai` | |
| Google Gemini | `@google/genai` | |
| Google Vertex AI | API key：`@google/genai`（`vertexai: true`）；服務帳戶 JSON：瀏覽器直接打 REST（`src/narrator/vertexAuth.ts`） | 兩種認證：① 快速模式（express mode）的 API key，送到 `aiplatform.googleapis.com`。② 服務帳戶 JSON（和 SillyTavern 的 Vertex AI「完整模式」一樣，例如贈金的專案）：在 key 欄位貼上或選擇金鑰檔，用私鑰在瀏覽器裡簽 RS256 的 JWT（WebCrypto），向 `oauth2.googleapis.com/token` 換 access token（快取到過期前一分鐘），再呼叫 `{區域}-aiplatform.googleapis.com/v1/projects/{專案}/locations/{區域}/publishers/google/models/{模型}:streamGenerateContent?alt=sse`；區域預設 us-central1，也可以填 global。兩個端點都允許瀏覽器跨網域呼叫，所以不需要伺服器。服務帳戶可以載入模型清單（`v1beta1/publishers/google/models`，只收 OAuth，只留 gemini 開頭的）；API key 不能列，要直接輸入模型名稱。兩種都有「測試連線」：用選的模型送一個很短的請求（`testConnection`），確認 key 與模型名稱 |
| OpenAI 相容格式 | `openai`（自訂 Base URL） | 內建 OpenRouter、DeepSeek、Ollama、LM Studio、智譜 GLM（BigModel、Z.ai）、通義千問（DashScope）、Moonshot 的預設網址（`providerInfo.ts`）；本機服務可不填 key |

「載入模型清單」會向服務查詢可用模型，也可以當作連線測試（Vertex AI 用 API key 時沒有這個按鈕，改用「測試連線」送一個很短的請求）。成人向的世界書條目與提示詞只在成人場景送出（第 5 節）；帶親密場景的日誌交給「成人場景正文」的來源，請確認那個服務的使用政策允許此類內容。

## 1. 七種請求

會呼叫 AI 的開關都在「設定 → 敘事與判定」的「AI 判定與描述」（`src/components/AiToggles.vue`），冒險頁面的「AI 判定」「AI 細節描述」按鈕打開的泡泡視窗是同一組開關：

- **擲骰的行動交給 AI 判定**（`aiJudge`）：請求 B。涵蓋的地方列在 `settings.ts` 的 `AI_JUDGED_PLACES`。
- **AI 設計**（`aiDesign.roster` / `shop` / `negotiation`）：請求 C、D、E，各自開關。舊版設定沒有這三項時沿用當時的 `aiJudge`。
- **AI 細節描述：自動寫出經過**（`aiNarration`）與日誌種類（`narrateKinds`）：請求 A。

每項還要它用的模型來源設定好（「功能分配」）才會呼叫。

| 請求 | 什麼時候 | 寫正文嗎 | 帶世界書 | 帶文風、其他提示詞 | 輸出 |
|---|---|---|---|---|---|
| **A. 敘事** | 日誌產生後（依「AI 細節描述」與日誌種類的開關；AI 判定的主動行動只看「主動行動」這個種類開關），或在日誌上按「✍️ 寫出經過」 | ✅ | ✅ | ✅ | 小說正文（＋選用的關係更新提議） |
| **A′. 成人場景敘事** | 日誌帶 `narration.adult_scene`（親密場景）時，取代 A | ✅ | ✅ | ✅（套用到「成人場景」的條目） | 小說正文，附上成人場景規則 |
| **B. 主動行動判定** | 開啟「擲骰的行動交給 AI 判定」，擲骰之後 | 預設不寫（勾選「判定時順便寫出經過」時寫在 `narrative` 欄位） | 選用（預設不帶） | 文風只有順便寫經過時；其他提示詞一律帶 | JSON |
| C. 居民潤飾 | 「AI 設計 → 居民」開啟，到達一個地點而名單上有還沒潤飾過的人（第一次來，或新搬來的居民） | ❌ | ❌ | ❌ | JSON |
| D. 商店清單 | 「AI 設計 → 商店清單」開啟，第一次進店 | ❌ | ❌ | ❌ | JSON |
| E. 談判方式 | 「AI 設計 → 談判方式」開啟，開始談判時 | ❌ | ❌ | ❌ | JSON |
| F. 插圖提示詞預處理 | 生成形象插圖、這個生圖服務選了預處理指示時 | ❌ | ❌ | ❌ | 依指示：Danbooru 標籤、英文描述、JSON 或自訂格式（見 [`PORTRAITS.md`](PORTRAITS.md) 第 3 節） |

會出現在日誌裡的正文只有 **A**（含 A′）與 **B**，所以文風、其他提示詞只套用到這幾種：每個條目可以選擇套用到「敘事」「成人場景」「判定」（第 6 節）。

### 模型來源與功能分配

「⚙️ 設定」可以設定三個**模型來源**（各自的服務、key、模型、最大輸出 tokens），再指定每個功能用哪一個來源（`settings.routes`，程式在 `src/stores/settings.ts`）：

| 功能 | 對應的請求 | 建議 |
|---|---|---|
| ✍️ 敘事正文 | A（包括主動行動判定之後的經過） | 寫作能力好的模型 |
| ✍️ 成人場景正文 | A′ | 願意寫成人內容的模型；預設和敘事正文同一個來源 |
| 🧮 主動行動判定 | B | 便宜的模型也可以 |
| 🧮 居民潤飾 | C | 便宜的模型 |
| 🧮 商店清單 | D | 便宜的模型 |
| 🧮 談判方式 | E | 便宜的模型 |
| 🧮 插圖提示詞預處理 | F | 便宜的模型 |

- **預設：判定與正文分開**。判定的 system 是「不需要寫經過，narrative 填空字串」，也不帶文風，只回傳 JSON；判定完成後，主動行動的報告（含判定的 rationale、twist、summary）和其他日誌一樣交給敘事請求（A），由「敘事正文」的來源寫出經過。這樣所有正文都出自同一套敘事提示詞（文風、世界書、人際關係），每次主動行動兩次呼叫，判定可以用便宜的模型。
- **判定時順便寫出經過**（設定裡的勾選，只有判定與正文同一個來源時有效）：判定時在 `narrative` 欄位直接寫出經過，省一次呼叫。
- **哪些日誌自動寫出經過**：設定的「AI 細節描述」底下可以分種類開關（主動行動、戰鬥、旅行、事件與委託、休息、交流、交易；預設交易以外都開）。AI 判定的主動行動只看「主動行動」這個開關，不受「AI 細節描述」總開關影響。任何日誌都可以手動按「✍️ 寫出經過」。
- **成人場景正文**：判定與敘事分開時，帶親密場景的日誌（娼館、主人的邀約、戰敗後的遭遇、AI 判定填了 `adult_scene` 的行動）交給這個來源寫。勾選「判定時順便寫出經過」時，如果判定的結果是親密場景、而成人場景正文是另一個來源，判定寫的經過不採用，改由成人場景正文的來源重寫。舊版設定沒有這一項時，用敘事正文的來源。
- 舊版的單一服務設定會變成「來源 1」，來源 2、3 先複製一份（只要改模型就好）。

### 思考（reasoning）與思考過程

每個模型來源可以設定**思考強度**（預設＝不送參數、關閉、低、中、高），以及要不要**在日誌顯示思考過程**（預設開啟）。各家的寫法不同（程式在 `src/narrator/providerInfo.ts`）：

| 服務 | 送出的參數 | 思考過程 |
|---|---|---|
| Anthropic | Claude 5 系列與 4.6 之後：`thinking: {type: "adaptive", display: "summarized"}`＋`output_config.effort`（關閉送 `disabled`；Opus 5.5、Fable、Mythos 不能關閉）；舊模型：`thinking.budget_tokens`（2048／8192／16384） | `thinking_delta` |
| OpenAI | `reasoning_effort`（關閉＝minimal） | 不回傳 |
| Gemini、Vertex AI | `thinkingConfig.thinkingBudget`（Gemini 3 用 `thinkingLevel`）、`includeThoughts` | `thought` 為 true 的部分 |
| OpenAI 相容格式 | 依「參數格式」：`reasoning_effort`、`thinking.type`（智譜 GLM、Kimi）、`reasoning.effort`（OpenRouter）、`enable_thinking`（通義千問）；自動時依 Base URL 判斷 | `reasoning_content`（DeepSeek、GLM、千問）或 `reasoning`（OpenRouter） |

OpenAI 相容格式另外可以填**自訂請求參數**（JSON 物件），直接加進請求，用來補上服務要求的其他欄位。

服務有回傳思考過程時，日誌卡片上會多一個摺疊的「💭 思考過程」，判定與敘事分開顯示（存在進行中遊戲的日誌敘事 `narrations` 的 `thinking` 與 `judgeThinking`，見 [SAVES](SAVES.md) 第 1 節）。

## 2. 排列順序與快取

各家服務都會快取「和上一次相同的開頭」：開頭一樣的部分，第二次起計費便宜很多、回應也比較快。所以提示詞依「多久變一次」排列，不太變動的放前面，常變動的放後面：

```
system（前段：同一局幾乎不變，可以被快取）
  1. 規則（敘事規則／判定規則）    ← 不含任何隨報告或行動改變的數字
  2. 文風（所有開啟的文風條目）    ← 接在規則最後，當作規則的一條（預設敘事規則用 {{style}} 放在硬性規則第 11 條；判定見第 4 節）
     （判定：輸出格式）
  3. 世界書（常駐條目）
  4. 其他提示詞（前段）
  5. （只有成人場景）世界書（成人向的常駐條目）
  6. （只有部分日誌或判定）戰敗事件規則、成人場景規則
user（後段：每次不同）
  7. 主角設定（敘事）／主角與隊伍狀態（判定）；成人向的日誌與判定另外附上慾望指標（[LEWD_STATS](LEWD_STATS.md)）
  8. 世界書（這次觸發的條目）
  9. 人際關係與冒險記憶
 10. （開啟「前後銜接」時）上一段正文的結尾、幕間
 11. 報告（敘事）／對象、行動、骰值、機制、可用的 effects（判定）
 12. 其他提示詞（後段）
 13. 本次要求：視角、篇幅、這次的寫法、玩家意圖、描寫重點
```

- 戰敗事件規則與成人場景規則只有部分日誌（判定）才有，敘事與判定都放在 system 的最後：前面的規則、文風、常駐世界書、前段提示詞和一般日誌一字不差，可以共用快取（以前放在規則後面、世界書前面，每次親密場景都讓後面約 6000 tokens 的常駐世界書沒有命中）。
- 成人向的常駐世界書條目只在成人場景注入，放在一般的常駐世界書與前段提示詞之後（`lore_adult`），一般日誌與成人場景的前段仍然一字不差。
- 成人場景用自己的一套條目（套用到「成人場景」）：條目和一般敘事相同時，開頭仍然共用；文風不同時從文風那裡開始分岔，一般敘事與成人場景各自快取一份前段。成人場景正文用另一個模型來源時，兩個來源的 system 各自固定，快取互不干擾。

- 以前放在 system 的視角、篇幅（隨報告改變）、判定的參考 DC、效果上限（隨主角等級改變）與可學能力清單，都移到後段，system 在同一局裡保持一字不差。
- Anthropic：在 system 尾端設定快取斷點（`cache_control: {type: "ephemeral"}`）。前段要超過約 1024～4096 tokens（依模型）才會被快取，5 分鐘內沒有再用就會失效。敘事請求帶常駐世界書，前段約 6000 tokens；判定請求不帶世界書時前段約 1000 tokens，可能不夠長而不會被快取。
- OpenAI、DeepSeek、直連的 Gemini（2.5 之後的模型）：自動快取相同的開頭，不需要額外設定。
- **手動標記（OpenAI 相容格式）**：有些服務要在請求裡標出快取斷點才會快取，例如 OpenRouter 上的 Gemini 與 Claude、阿里雲百煉的通義千問顯式快取。模型來源的「提示詞快取標記」（`cacheMark`）設定要不要標：
  - 自動（預設）：模型名稱有 gemini、claude、anthropic，或 Base URL 是百煉而模型是千問時標記；其他（例如 DeepSeek）不標。
  - 標記：system 改成內容陣列，在尾端加上 `cache_control: {type: "ephemeral"}`（`src/narrator/providers.ts` 的 `openAIMessages`）。
  - 標記並保留 1 小時：加上 `ttl: "1h"`（只有 Claude 支援，寫入費用較高）。
  - 不標記：服務會自動快取，或不認得這個欄位而報錯時。
  - Gemini 經 OpenRouter 只認最後一個斷點，而且前段要超過約 4096 tokens 才會寫入快取（約 5 分鐘有效）：敘事請求的前段夠長，判定請求通常不夠。
- 每則日誌下方的 token 統計會標示讀到快取的數量（服務有回報時），並依功能與來源（模型來源名稱、服務、模型）分開列出；日誌上方列出本局依來源的合計。來源記在用量上（`usage` 的 `by`），之後改了設定也不影響舊紀錄。
- 前段任何一個字改變（開關文風、修改常駐世界書），快取就要重新建立一次；常常要換的指示請放在「其他提示詞（後段）」。

## 3. A. 敘事請求

### 規則（system 第一段）

玩家可以在提示詞頁籤的「📜 敘事規則」直接修改這段（存在目前提示詞組的 `narrationRules`，沒有修改時用 `DEFAULT_NARRATION_RULES`），「恢復預設」清掉修改。代換：`{{language}}` 輸出語言、`{{currency}}` 貨幣說明、`{{player}}` 主角名、`{{style}}` 文風的位置（沒有時接在規則最後）；文風的前綴接續它前一行的編號或項目符號（「10.」→「11. 文風」、「-」→「- 文風」，其他只寫「文風」）。視角與篇幅寫在每次的「本次要求」，規則裡不要寫死。預設第 10 條 `<relationship_updates>` 的格式由程式讀取，改掉會讓人際關係更新失效。判定規則不開放修改。成人向的戰敗事件另外附加「戰敗事件規則」（同一頁的第二個文字框，也可以修改、恢復預設）：戰報停在敵人動手的前一刻（`narration.mode = defeat_cliffhanger`），玩家回應之後的經過是後半段（`defeat_event`，AI 判定的 narrative 也會用）。

成人向的**親密場景**另外附加「成人場景規則」（第三個文字框，`sceneRules`，預設 `DEFAULT_SCENE_RULES`，可以修改、恢復預設），要求把場景當作正文的主體詳細描寫，篇幅至少「中」（約 500～900 字）。報告帶 `narration.adult_scene`（場景是什麼）時附上，本次要求會多一行「成人場景：……」。會標記的情況：

| 情況 | 何時 |
|---|---|
| 娼館消費（patron） | 一律 |
| 在娼館工作（work，站在娼館） | 一律 |
| 主人的邀約（proposition）「答應」 | 一律；推辭、拒絕不會 |
| 被主人推進娼館（brothel_forced） | 順從一律；哀求、拒絕在檢定失敗時 |
| 戰敗事件的回應（defeat_event） | 失敗、大失敗（沒能脫身）；部分成功由 AI 決定 |
| 其他行動（自由行動、長休的互動、自己描述的主人事件回應……） | AI 判定在 JSON 填 `adult_scene` 時 |

主人事件的選項用 `slavery.json` 的 `scene`（事件的場景名稱）與選項的 `adult_scene`（`always` / `success` / `fail`）設定。主動行動的 setup 用 `content.ts` 的 `adultScene(label, on)` 標出可能的場景（`on` 是會進入場景的成功程度，空陣列表示交給 AI 判定）。判定請求的前段也會附上這段規則與 `adult_scene` 欄位的說明（只在 AI 填了 `adult_scene` 時適用）。

```
你是奇幻 RPG《埃隆迪亞大陸》的敘事者……

硬性規則：
1. 報告的結果、數值、物品、傷亡、時間不可更改，不可新增
2. 依 timeline 順序描寫；擲骰與 DC 不寫數字，改以描寫呈現
3. 親密值不寫數字；attitude 是態度基調、personality 是性格
4. 視角與篇幅依最後的「本次要求」；分段，段落長短交錯
5. 只輸出正文，不要標題、狀態欄、思考過程
6. 使用繁體中文／简体中文（設定）
7. 以世界書為準，忽略世界書裡聊天用的「格式」「狀態欄」指示
8. <protagonist>、<relationships>、<memories> 的用法
9. 有 <relationships> 時，正文後可附 <relationship_updates>
10. 文風（除了上面的硬性規則之外最優先遵守；有多種時融合使用）：<style>……</style>
```

文風放在規則裡、排在世界書前面：世界書有數千字，文風如果放在它後面，離規則太遠，AI 比較容易忽略。

### 後段

| 區塊 | 內容 | 來源 |
|---|---|---|
| `<protagonist>` | 主角的名字、性別、種族職業等級、出身、外貌、背景 | 建角時填寫、隊伍視窗可改 |
| `<worldbook>`（觸發） | 這次觸發的世界書條目 | 見第 5 節 |
| `<relationships>` | 參與人的外貌、性格、與主角／他人的關係、親密度階段 | 人際關係 |
| `<memories>` | 最多 6 筆相關記憶（時間｜地點｜參與人｜簡述） | 共同記憶檢索 |
| `<previous>` | 上一段正文的結尾（約 300 字） | 前後銜接（3.1 節） |
| `<interlude>` | 上一段正文之後、這次事件之前沒有寫成正文的事 | 前後銜接（3.1 節） |
| `<report>` | 報告 JSON（id 換成中文名稱） | 遊戲引擎 |
| `<notes>` | 放在後段的其他提示詞 | 提示詞頁籤 |
| 本次要求 | 視角（`narration.pov`）、篇幅（`narration.length` 依「正文篇幅」換成字數）、這次的寫法（3.2 節）、前後銜接的說明、玩家意圖、描寫重點 | 報告、提示詞設定 |

篇幅有三檔，報告的 `narration.length` 決定用哪一檔：自由行動是中篇，親密場景至少中篇，其他多數是短篇。字數依提示詞設定的**正文篇幅**（`lengthScale`，「📜 敘事規則」最上面）：

| 正文篇幅 | 短篇 | 中篇 | 長篇 |
|---|---|---|---|
| 偏短 | 約 150～300 字 | 約 400～700 字 | 約 800～1200 字 |
| 標準（預設） | 約 200～400 字 | 約 500～900 字 | 約 1000～1500 字 |
| 偏長 | 約 400～700 字 | 約 900～1400 字 | 約 1500～2200 字 |

### 3.1 前後銜接

提示詞設定的「前後銜接」（`continuity`，預設開啟）開啟時，敘事與判定都帶上（`src/narrator/continuity.ts`）：

- `<previous>`：往回找最近一則寫好正文的日誌（最多看 20 則；只是存判定思考過程的空敘事、還在串流或失敗的不算），取正文最後約 300 字，從段落或句子的開頭切。本次要求要 AI 從它之後接著寫，不重寫、不摘要，開場與收尾不用一樣的句式。
- `<interlude>`：那則日誌之後、這次事件之前的事，依時間排列：沒有正文的日誌（最近 8 則）各一行（時間｜地點｜摘要，主動行動加上玩家的描述）；中間走過的地方合成一行「移動：來到 A，再到 B」；最後一行是距離上一段正文過了幾小時（一小時以上時）。本次要求要 AI 在開頭用一兩句自然帶過，不逐條複述、不改寫結果。
- 走過的地方記在存檔的 `trail`（`grid.ts` 的 `noteSpot`）：每走一步或換區時，區域名稱（站在設施、地標上時加上它的名字）和上一筆不同才記，只留最近 12 筆；旅途上不記。
- 成人場景的分流：這次不是成人場景（敘事不帶 `adult_scene`、判定不是可能進入親密場景的行動）時，帶親密場景的日誌不送原文：`<previous>` 換成「（一段私密的時光，已經結束）」，`<interlude>` 裡那則日誌的摘要也換成這句，所以一般來源不會收到成人向的文字。成人場景的請求照常帶原文。
- 判定時，本次要求說明這兩段是行動之前剛發生的事，判定時可以參考；順便寫經過時也照著銜接。
- 兩段都在後段，不影響前段的快取，每次多送幾百字。在日誌上手動「✍️ 寫出經過」時，以那則日誌在日誌裡的位置往回找。

### 3.2 這次的寫法

提示詞設定的「變化正文的寫法」（`variety`，預設開啟）開啟時，本次要求多一行「這次的寫法」：開場（從對白開場、從動作中途切入、從感官細節、從同伴或旁人的反應、從主角的念頭、從環境或時間的變化、開門見山）與收尾（停在畫面、對白、動作、還沒說破的細節、主角的反應）各自依日誌編號輪替，連續兩則不會一樣（`prompt.ts` 的 `varietyHint`）。戰敗事件的前半段只指定開場（收尾已經規定停在懸念上）。判定時順便寫經過的 narrative 也有（用等待中行動的編號）。預設敘事規則的 execution 也要求開場與收尾照這一行、每次換一種，negative 列出要少用的套話。

## 4. B. 主動行動判定請求

### 規則（system 第一段）

```
你是……判定者兼敘事者……只輸出一個 JSON 物件。
1～2. 骰值是參考，可以出乎預料
3～5. degree、attr、dc（<dice> 參考值 ±3）、effects（只能用 <effects_allowed> 列出的）
6.    玩家描述只代表「嘗試」
7.    一次行動要把玩家描述的事做到有結果；沒有對手、沒有風險的事不順利時，傾向部分成功加代價
8.    difficulty：<action> 註明時，日常小事填 trivial（結果至少是成功），其他填 normal
9.    hours：<action> 註明時，依經過估計花了多少小時
10.   narrative 用設定的語言；視角與篇幅依「本次要求」；不寫骰值與數字
11.   <inventory> 行囊：合理用到行囊裡的道具可以調低 DC；沒有的道具當作沒有
      貨幣只有白鸛幣（舊幣制換算、大約的物價）
12.   只輸出 JSON
13.   文風（narrative）：<style>……</style>（只有順便寫經過時；編號接續規則的最後一條，和敘事規則一樣用 styleLead）
輸出格式：{"degree":…,"narrative":"……",…}
……常駐世界書、其他提示詞（前段）……
（有需要時，放在 system 的最後：成人向的常駐世界書、戰敗事件規則、成人場景規則）
```

戰敗事件規則與成人場景規則只有部分判定才有，和敘事請求一樣放在 system 的最後，前面的規則、文風、輸出格式、常駐世界書、前段提示詞可以共用快取。

### 後段

| 區塊 | 內容 |
|---|---|
| `<actor>` | 主角的種族職業等級、性別、出身、外貌、背景、五屬性、技能、金錢、契約 |
| `<party>` | 每位隊員的入隊方式、性別、種族職業、HP、裝備、狀態、對主角的態度 |
| `<inventory>` | 隊伍行囊（工具模板會標出來） |
| `<worldbook>`（觸發） | 「判定請求也帶世界書」開啟時；比對行動描述、場景、地點、對象的名字與性格 |
| `<relationships>`、`<memories>` | 隊伍全員與行動對象，加上目前地點 |
| `<previous>`、`<interlude>` | 開啟「前後銜接」時（3.1 節） |
| `<target>` | 對象的資料與人際關係 |
| `<action>` | 行動名稱、場景、出價、玩家描述、長休互動的說明、搭配使用的能力；自由行動另外註明可以判為日常小事、花費時間的範圍（[ACTIONS](ACTIONS.md) 第 1 節） |
| `<dice>` | 自然骰、情境修正、各屬性總值、參考 DC 與可標示的範圍、依預設屬性的參考結果 |
| `<mechanics>` | 各成功程度在程式中會發生什麼 |
| `<effects_allowed>` | 這種行動可用的 effects 與上限（隨主角等級改變） |
| `<notes>`、本次要求 | 後段的其他提示詞；narrative 的視角（第二人稱）、篇幅（自由行動是中篇，其他是短篇，依「正文篇幅」換成字數）與這次的寫法 |

判定請求預設不帶世界書，大小主要來自主角、隊伍、人際關係、記憶與規則；隊伍與人際關係越多越大。開啟「判定請求也帶世界書」後，世界觀更一致，但每次行動多送數千字（常駐條目在前段，可以被快取）。

## 5. 世界書

內建世界書是簡體寫的；送出前依「AI 的輸出語言」轉換寫法：輸出繁體時世界書轉成繁體，輸出簡體時整份敘事與判定的提示詞都轉成簡體（逐字轉換，轉換後的內容一樣可以被快取，見 [I18N](I18N.md) 第 4 節）。

每個條目有一種注入方式，可以在提示詞頁籤修改：

| 方式 | 意思 | 位置 |
|---|---|---|
| 常駐 | 每次都注入 | 前段 |
| 關鍵字觸發 | 報告（或判定的行動）文字命中關鍵字時注入；世界書是簡體，比對時繁簡兩種寫法都比 | 後段 |
| 旅行報告 | 只有旅行報告注入 | 後段 |
| 停用 | 不注入 | — |

預設值：

| 條目 | 預設 |
|---|---|
| 埃隆迪亞大陸、區域地理與勢力概述、神祇信仰 | 常駐 |
| 視角和文風條目 | 停用（改由文風條目管理；需要時可以開啟） |
| 區域地理地標相對位置 | 旅行報告 |
| 高維巨龍 | 關鍵字「龍」 |
| 規則類條目（親密值、公會等級、力量體系、職業、技能、COT、格式規範、角色扮演指導） | 停用（已經由遊戲引擎實作，或和介面衝突） |
| 敘事傾向、情色喜劇法則 | 常駐，成人向（只在成人場景注入） |
| 暗殺、娼妓、奴隸的價格參考 | 關鍵字，成人向 |
| 其他條目 | 關鍵字（貨幣說明由規則的 `{{currency}}` 提供，世界書原本的「价格参考-货币体系」已刪除，因為它寫的是四種貨幣，和只有白鸛幣衝突） |

- 注入順序依 order（越小越前面）；常駐條目一律排在觸發條目前面，超過字數上限時優先保留。
- **成人向**的條目只在成人場景注入：敘事是帶親密場景（`adult_scene`）的日誌，判定是可能進入親密場景的行動（setup 標了 `adultScene`：娼館、主人的要求、戰敗事件……）。自由行動的判定不帶成人向條目，但 AI 照樣可以填 `adult_scene`，之後的正文就是成人場景。
- 頁籤會依選擇的日誌（或判定的行動）顯示每個條目的狀態：常駐、觸發（命中的關鍵字）、未觸發、停用、成人（不是成人場景）、超出字數上限，以及注入順序。
- 可以修改內建條目的名稱、關鍵字、內容、order、成人標記（可以恢復預設），也可以新增自己的條目。
- 內容裡的「沈頤」（世界書寫死的玩家名）與 `{{player}}` 會換成主角名字。
- **匯出世界書**：SillyTavern 世界書格式（含修改與新增的條目，常駐 → `constant`、停用 → `disable`），本遊戲的注入方式與成人標記放在每個條目的 `extensions.elondia`，酒館會忽略。
- **匯入世界書**：SillyTavern 世界書或本遊戲匯出的檔案，可以一次選多個。本遊戲匯出的內建條目會還原成匯出時的修改；其他條目加成自訂條目（`constant` → 常駐、`disable` → 停用，其餘為關鍵字觸發）；內容和現有條目完全相同的略過。

## 6. 文風與其他提示詞

- **套用到**：敘事（一般日誌）、成人場景（帶親密場景的日誌，取代「敘事」）、判定，可以多選。內建條目（「範例：額外提醒」只套用到敘事與成人場景）與新增的條目預設三種都套用；舊的設定（`version` 1）與匯入的舊檔案，套用到敘事的條目自動加上成人場景，行為和以前一樣。想讓成人場景換一套文風時，把一般文風的「成人場景」取消，另外建一個只套用到成人場景的文風。
- **🔞 成人向**：勾選的條目只在成人場景送出（和世界書的成人標記一樣，見第 5 節）。
- **文風**：常駐提示詞，可以存多個、自由開關、修改、排序。開啟的文風依序合併成一個 `<style>` 區塊，接在硬性規則的最後當作規則的一條，排在世界書前面，以提高遵循度。內建十二種：
  - 一般：埃隆迪亞・史詩奇幻（預設開啟）、日輕第一視角・吐槽與心跳（預設開啟）、輕小說、黑暗寫實、詼諧冒險。
  - 成人向（標記為成人向，只在成人場景送出）：共通層・直白肉體（NSFW 底座）、肥膩肉感・濃稠與氣味、淫語・台詞的色情匯報（以上預設開啟）、羞恥・理智崩解、現代直白・逐幀與人設鐵律、反差 × 戀物・衣裝與凝視、文言古風・道袍與春宮。
  - 舊的提示詞設定不會自動多出新的內建文風：在文風清單按「加回內建條目」（加回來的預設是關閉的）。
- **其他提示詞**：和文風一樣，但不限類型（角色口癖、想避開的題材、格式偏好……），而且可以選擇放在前段（`<instructions>`，可以被快取）或後段（`<notes>`，每次請求的最後，AI 比較不容易忘記）。
- 內容可以用 `{{player}}` 代表主角名字。
- **匯出**：文風、其他提示詞可以各自匯出全部或只匯出開啟的（`{"type":"elondia-styles","entries":[…]}`）。
- **匯入**：本遊戲匯出的檔案、條目陣列或整份提示詞設定；也可以匯入 `.txt`、`.md`，整份當作一個條目、檔名當名稱。匯入的條目加在清單最後，名稱與內容都相同的略過。
- **匯入酒館預設**（`src/narrator/tavernPreset.ts`、`TavernPresetDialog.vue`）：SillyTavern 的對話補全預設（`prompts` 依全域的 `prompt_order` 排序；聊天紀錄之類的標記與空的條目不列）、舊版的 `main_prompt`／`nsfw_prompt`／`jailbreak_prompt`，或系統提示詞預設（`name` + `content`）。對話框列出每個條目（預設裡有沒有開、酒館用哪個身分送出、是否在聊天紀錄之後、內容），勾選後加到文風或其他提示詞，可以分幾次加到不同地方，也可以合併成一個條目；套用到、成人向、加進來就開啟一次設定。`{{user}}`／`<USER>` 換成 `{{player}}`，`{{// 註解}}`、`{{trim}}`、`{{noop}}` 拿掉，`{{newline}}` 換行；其他巨集（`{{char}}`、`{{setvar::…}}`……）原樣保留並在條目上標出來。加到其他提示詞時，酒館放在聊天紀錄之後（或 `injection_position` 是聊天中）的條目放後段，其他放前段。預設不套用到判定（判定要求只輸出 JSON）。
- 這些設定跟著瀏覽器走（所有存檔共用），存在目前的提示詞組（localStorage 的 `elondia.promptSets`）；頁籤底部可以一次匯出、匯入全部設定（匯入會取代目前的設定）或全部恢復預設。

## 7. C～E. 生成請求

只輸出 JSON，內容是名字、外貌、性格（酒館）、交易清單（商店）、談判方式（談判），不會出現在日誌正文裡，所以不套用文風與其他提示詞。
