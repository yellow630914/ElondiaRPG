# 發給 AI 的提示詞結構

> 這份文件整理所有送給 AI 的請求。程式碼在 `src/narrator/prompt.ts`（敘事）、`src/narrator/judge.ts`（判定與生成）、`src/narrator/lore.ts`（世界書）、`src/narrator/promptConfig.ts`（文風與其他提示詞）、`src/narrator/compose.ts`（依設定組合）。玩家在遊戲上方的「🧩 提示詞」頁籤調整與預覽。

## 1. 五種請求

| 請求 | 什麼時候 | 寫正文嗎 | 帶世界書 | 帶文風、其他提示詞 | 輸出 |
|---|---|---|---|---|---|
| **A. 敘事** | 日誌產生後（依「AI 細節描述」與日誌種類的開關；AI 判定的主動行動一律會寫），或在日誌上按「✍️ 寫出經過」 | ✅ | ✅ | ✅ | 小說正文（＋選用的關係更新提議） |
| **B. 主動行動判定** | 開啟「AI 判定主動行動」，主動行動擲骰之後 | 預設不寫（勾選「判定時順便寫出經過」時寫在 `narrative` 欄位） | 選用（預設不帶） | 只有順便寫經過時 | JSON |
| C. 居民潤飾 | AI 判定開啟，第一次到一個地點（名單上的人一次潤飾） | ❌ | ❌ | ❌ | JSON |
| D. 商店清單 | AI 判定開啟，第一次進店 | ❌ | ❌ | ❌ | JSON |
| E. 談判方式 | AI 判定開啟，開始談判時 | ❌ | ❌ | ❌ | JSON |

會出現在日誌裡的正文只有 **A** 與 **B**，所以文風、其他提示詞只套用到這兩種（每個條目可以選擇套用到哪一種）。

### 模型來源與功能分配

「⚙️ 設定」可以設定三個**模型來源**（各自的服務、key、模型、最大輸出 tokens），再指定每個功能用哪一個來源（`settings.routes`，程式在 `src/stores/settings.ts`）：

| 功能 | 對應的請求 | 建議 |
|---|---|---|
| ✍️ 敘事正文 | A（包括主動行動判定之後的經過） | 寫作能力好的模型 |
| 🧮 主動行動判定 | B | 便宜的模型也可以 |
| 🧮 居民潤飾 | C | 便宜的模型 |
| 🧮 商店清單 | D | 便宜的模型 |
| 🧮 談判方式 | E | 便宜的模型 |

- **預設：判定與正文分開**。判定的 system 是「不需要寫經過，narrative 填空字串」，也不帶文風，只回傳 JSON；判定完成後，主動行動的報告（含判定的 rationale、twist、summary）和其他日誌一樣交給敘事請求（A），由「敘事正文」的來源寫出經過。這樣所有正文都出自同一套敘事提示詞（文風、世界書、人際關係），每次主動行動兩次呼叫，判定可以用便宜的模型。
- **判定時順便寫出經過**（設定裡的勾選，只有判定與正文同一個來源時有效）：判定時在 `narrative` 欄位直接寫出經過，省一次呼叫。
- **哪些日誌自動寫出經過**：設定的「AI 細節描述」底下可以分種類開關（主動行動、戰鬥、旅行、事件與委託、休息、交流、交易；預設交易以外都開）。AI 判定的主動行動只看「主動行動」這個開關，不受「AI 細節描述」總開關影響。任何日誌都可以手動按「✍️ 寫出經過」。
- 舊版的單一服務設定會變成「來源 1」，來源 2、3 先複製一份（只要改模型就好）。

## 2. 排列順序與快取

各家服務都會快取「和上一次相同的開頭」：開頭一樣的部分，第二次起計費便宜很多、回應也比較快。所以提示詞依「多久變一次」排列，不太變動的放前面，常變動的放後面：

```
system（前段：同一局幾乎不變，可以被快取）
  1. 規則（敘事規則／判定規則）    ← 不含任何隨報告或行動改變的數字
  2. 文風（所有開啟的文風條目）    ← 接在規則最後，當作規則的一條（敘事第 10 條、判定第 9 條）
     （判定：輸出格式）
  3. 世界書（常駐條目）
  4. 其他提示詞（前段）
user（後段：每次不同）
  5. 主角設定（敘事）／主角與隊伍狀態（判定）
  6. 世界書（這次觸發的條目）
  7. 人際關係與冒險記憶
  8. 報告（敘事）／對象、行動、骰值、機制、可用的 effects（判定）
  9. 其他提示詞（後段）
 10. 本次要求：視角、篇幅、玩家意圖、描寫重點
```

- 以前放在 system 的視角、篇幅（隨報告改變）、判定的參考 DC、效果上限（隨主角等級改變）與可學能力清單，都移到後段，system 在同一局裡保持一字不差。
- Anthropic：在 system 尾端設定快取斷點（`cache_control: {type: "ephemeral"}`）。前段要超過約 1024～4096 tokens（依模型）才會被快取，5 分鐘內沒有再用就會失效。敘事請求帶常駐世界書，前段約 6000 tokens；判定請求不帶世界書時前段約 1000 tokens，可能不夠長而不會被快取。
- OpenAI、Gemini：自動快取相同的開頭，不需要額外設定。
- 每則日誌下方的 token 統計會標示讀到快取的數量（服務有回報時）。
- 前段任何一個字改變（開關文風、修改常駐世界書），快取就要重新建立一次；常常要換的指示請放在「其他提示詞（後段）」。

## 3. A. 敘事請求

### 規則（system 第一段）

玩家可以在提示詞頁籤的「📜 敘事規則」直接修改這段（存在 `elondia.prompts` 的 `narrationRules`，沒有修改時用 `DEFAULT_NARRATION_RULES`），「恢復預設」清掉修改。代換：`{{language}}` 輸出語言、`{{currency}}` 貨幣說明、`{{player}}` 主角名、`{{style}}` 文風的位置（沒有時接在規則最後）；文風的前綴接續它前一行的編號或項目符號（「10.」→「11. 文風」、「-」→「- 文風」，其他只寫「文風」）。視角與篇幅寫在每次的「本次要求」，規則裡不要寫死。第 9 條 `<relationship_updates>` 的格式由程式讀取，改掉會讓人際關係更新失效。判定規則不開放修改。成人向的戰敗事件另外附加「戰敗事件規則」（同一頁的第二個文字框，也可以修改、恢復預設）：戰報停在敵人動手的前一刻（`narration.mode = defeat_cliffhanger`），玩家回應之後的經過是後半段（`defeat_event`，AI 判定的 narrative 也會用）。

```
你是奇幻 RPG《埃隆迪亞大陸》的敘事者……

硬性規則：
1. 報告的結果、數值、物品、傷亡、時間不可更改，不可新增
2. 依 timeline 順序描寫；擲骰與 DC 不寫數字，改以描寫呈現
3. 親密值不寫數字；attitude 是態度基調、personality 是性格
4. 視角與篇幅依最後的「本次要求」；分段
5. 只輸出正文，不要標題、狀態欄、思考過程
6. 使用繁體中文／简体中文（設定）
7. 以世界書為準，忽略世界書裡聊天用的「格式」「狀態欄」指示
8. <protagonist>、<relationships>、<memories> 的用法
9. 有 <relationships> 時，正文後可附 <relationship_updates>
10. 文風（除了上面的硬性規則之外最優先遵守；有多種時融合使用）：<style>……</style>
```

文風放在規則裡、排在世界書前面：世界書有數千字，文風如果放在它後面，離規則太遠，AI 比較容易忽略。

### 後段

| 區塊 | 內容 | 來源 |
|---|---|---|
| `<protagonist>` | 主角的名字、性別、種族職業等級、出身、外貌、背景 | 建角時填寫、隊伍視窗可改 |
| `<worldbook>`（觸發） | 這次觸發的世界書條目 | 見第 5 節 |
| `<relationships>` | 參與人的外貌、性格、與主角／他人的關係、親密度階段 | 人際關係 |
| `<memories>` | 最多 6 筆相關記憶（時間｜地點｜參與人｜簡述） | 共同記憶檢索 |
| `<report>` | 報告 JSON（id 換成中文名稱） | 遊戲引擎 |
| `<notes>` | 放在後段的其他提示詞 | 提示詞頁籤 |
| 本次要求 | 視角（`narration.pov`）、篇幅（`narration.length`）、玩家意圖、描寫重點 | 報告 |

## 4. B. 主動行動判定請求

### 規則（system 第一段）

```
你是……判定者兼敘事者……只輸出一個 JSON 物件。
1～2. 骰值是參考，可以出乎預料
3～5. degree、attr、dc（<dice> 參考值 ±3）、effects（只能用 <effects_allowed> 列出的）
6.    玩家描述只代表「嘗試」
7.    narrative 用設定的語言；視角與篇幅依「本次要求」；不寫骰值與數字
8.    只輸出 JSON
9.    narrative 的文風：<style>……</style>
輸出格式：{"degree":…,"narrative":"……",…}
```

### 後段

| 區塊 | 內容 |
|---|---|
| `<actor>` | 主角的種族職業等級、性別、出身、外貌、背景、五屬性、技能、金錢、契約 |
| `<party>` | 每位隊員的入隊方式、性別、種族職業、HP、裝備、狀態、對主角的態度 |
| `<worldbook>`（觸發） | 「判定請求也帶世界書」開啟時；比對行動描述、場景、地點、對象的名字與性格 |
| `<relationships>`、`<memories>` | 隊伍全員與行動對象，加上目前地點 |
| `<target>` | 對象的資料與人際關係 |
| `<action>` | 行動名稱、場景、出價、玩家描述、長休互動的說明、搭配使用的能力 |
| `<dice>` | 自然骰、情境修正、各屬性總值、參考 DC 與可標示的範圍、依預設屬性的參考結果 |
| `<mechanics>` | 各成功程度在程式中會發生什麼 |
| `<effects_allowed>` | 這種行動可用的 effects 與上限（隨主角等級改變） |
| `<notes>`、本次要求 | 後段的其他提示詞；narrative 的視角（第二人稱）與篇幅（約 200～400 字） |

判定請求預設不帶世界書，大小主要來自主角、隊伍、人際關係、記憶與規則；隊伍與人際關係越多越大。開啟「判定請求也帶世界書」後，世界觀更一致，但每次行動多送數千字（常駐條目在前段，可以被快取）。

## 5. 世界書

每個條目有一種注入方式，可以在提示詞頁籤修改：

| 方式 | 意思 | 位置 |
|---|---|---|
| 常駐 | 每次都注入 | 前段 |
| 關鍵字觸發 | 報告（或判定的行動）文字命中關鍵字時注入；世界書是簡體，比對時繁簡兩種寫法都比 | 後段 |
| 旅行報告 | 只有旅行報告注入 | 後段 |
| 停用 | 不注入 | — |

預設值：

| 條目 | 預設 |
|---|---|
| 埃隆迪亞大陸、區域地理與勢力概述、神祇信仰 | 常駐 |
| 視角和文風條目 | 停用（改由文風條目管理；需要時可以開啟） |
| 區域地理地標相對位置 | 旅行報告 |
| 高維巨龍 | 關鍵字「龍」 |
| 規則類條目（親密值、公會等級、力量體系、職業、技能、COT、格式規範、角色扮演指導） | 停用（已經由遊戲引擎實作，或和介面衝突） |
| 敘事傾向、情色喜劇法則 | 常駐，成人向（設定開啟才注入） |
| 暗殺、娼妓、奴隸的價格參考 | 關鍵字，成人向 |
| 其他條目 | 關鍵字 |

- 注入順序依 order（越小越前面）；常駐條目一律排在觸發條目前面，超過字數上限時優先保留。
- 頁籤會依選擇的日誌（或判定的行動）顯示每個條目的狀態：常駐、觸發（命中的關鍵字）、未觸發、停用、成人（未開啟）、超出字數上限，以及注入順序。
- 可以修改內建條目的名稱、關鍵字、內容、order、成人標記（可以恢復預設），也可以新增自己的條目。
- 內容裡的「沈頤」（世界書寫死的玩家名）與 `{{player}}` 會換成主角名字。
- **匯出世界書**：SillyTavern 世界書格式（含修改與新增的條目，常駐 → `constant`、停用 → `disable`），本遊戲的注入方式與成人標記放在每個條目的 `extensions.elondia`，酒館會忽略。
- **匯入世界書**：SillyTavern 世界書或本遊戲匯出的檔案，可以一次選多個。本遊戲匯出的內建條目會還原成匯出時的修改；其他條目加成自訂條目（`constant` → 常駐、`disable` → 停用，其餘為關鍵字觸發）；內容和現有條目完全相同的略過。

## 6. 文風與其他提示詞

- **文風**：常駐提示詞，可以存多個、自由開關、修改、排序，選擇套用到敘事、判定或兩者。開啟的文風依序合併成一個 `<style>` 區塊，接在硬性規則的最後當作規則的一條，排在世界書前面，以提高遵循度。內建四種：埃隆迪亞・史詩奇幻（預設開啟）、輕小說、黑暗寫實、詼諧冒險。
- **其他提示詞**：和文風一樣，但不限類型（角色口癖、想避開的題材、格式偏好……），而且可以選擇放在前段（`<instructions>`，可以被快取）或後段（`<notes>`，每次請求的最後，AI 比較不容易忘記）。
- 內容可以用 `{{player}}` 代表主角名字。
- **匯出**：文風、其他提示詞可以各自匯出全部或只匯出開啟的（`{"type":"elondia-styles","entries":[…]}`）。
- **匯入**：本遊戲匯出的檔案、條目陣列或整份提示詞設定；也可以匯入 `.txt`、`.md`，整份當作一個條目、檔名當名稱。匯入的條目加在清單最後，名稱與內容都相同的略過。
- 這些設定跟著瀏覽器走（所有存檔共用），存在 localStorage 的 `elondia.prompts`；頁籤底部可以一次匯出、匯入全部設定（匯入會取代目前的設定）或全部恢復預設。

## 7. C～E. 生成請求

只輸出 JSON，內容是名字、外貌、性格（酒館）、交易清單（商店）、談判方式（談判），不會出現在日誌正文裡，所以不套用文風與其他提示詞。
