# 任務／事件生成系統與 AI 權責劃分（提案 v0.1）

> 狀態：構想階段的設計建議。其中的主動行動已改為「擲骰先發生、AI 直接判定並寫出結果」並實作（見 [`RELATIONSHIP_MEMORY.md`](RELATIONSHIP_MEMORY.md) 第 5 節）；報酬模板已實作（見 [`COMPANIONS.md`](COMPANIONS.md) 第 1 節）；生成的 NPC 會登錄、可以再遇到與邀請。任務事件鏈與隨機事件尚未實作。文末有待決定事項。

## 0. 核心原則：AI 提案，程式裁決

目前的遊戲之所以穩定，是因為「引擎是唯一真相，AI 只負責描寫」。任務、事件與主動行動要給 AI 更大的空間，但這條原則不該破，只要改成：

> **AI 可以「提案」和「選擇」，但一切會改變遊戲狀態的事，都由程式驗證、擲骰、套用。**

具體做法是三條規則：

1. **AI 只輸出結構化資料，不輸出狀態變化。** AI 回傳的是 JSON（任務模板、行動意圖、選項），欄位與可用值都由程式事先給定（封閉詞彙）。程式驗證後才採用；不合格就要求重寫，再失敗就用預設值。
2. **數字由程式決定，AI 只能在範圍內微調。** DC、傷害、報酬、親密值變化都有預算表；AI 想加碼，只能在程式允許的區間內選。
3. **AI 的每一次決定都存檔。** 同一個事件不會因為重新生成敘事而改變結果；讀檔後一切可以重現。

AI 關閉時，每個環節都要有程式版的退路（從固定的模板池抽、從下拉選單選行動），遊戲仍然完整可玩。這也是測試穩定性最好的方法：**先讓整個系統在 AI 關閉時能跑，再讓 AI 去填同一個結構。**

## 1. 權責劃分總表

| 事項 | 程式 | AI |
|---|---|---|
| **何時**發生事件（機率、冷卻、節奏） | ✅ | |
| 事件**類別**與適用場景的篩選 | ✅ | |
| 任務的**結構**（事件鍊、旗標、報酬條件） | 驗證、補完、執行 | ✅ 編寫（離線或接任務時） |
| 名稱、描述、NPC 個性與台詞 | | ✅ |
| 檢定屬性、DC、敵人數值、報酬金額 | ✅ 預算與上限 | 在範圍內微調 |
| 解讀玩家的自由輸入 | 提供可用動詞與目標 | ✅ 轉成結構化意圖 |
| 擲骰、成敗等級 | ✅ | |
| 後果（親密值、聲望、旗標、戰鬥、物品） | ✅ 後果表與上限 | 從程式給的候選中挑選 |
| 事件經過的文字 | | ✅（現有的敘事器） |

一句話：**程式管「會不會、多少、成不成」，AI 管「是什麼、為什麼、怎麼說」。**

## 2. 模板定義

### 2.1 事件（Event）：一輪內結束

事件是單次發生、一次結算的情境（一場特殊遭遇戰、一個寶箱、一次邂逅）。結構：

```jsonc
{
  "id": "ev_wounded_pilgrim",
  "kind": "meeting",                 // encounter / discovery / chest / meeting / trap / choice
  "context": {
    "where": ["travel", "wild"],     // dungeon / wild / town / travel
    "places": [],                    // 城鎮事件的場所：tavern / temple / market / inn / gate …
    "regions": ["central"],
    "rank": ["F", "D"],              // 適用的公會階級範圍
    "time": ["day", "dusk"]
  },
  "weight": 10, "cooldown_days": 7, "once": false,
  "requires": { "flags_none": ["pilgrim_saved"] },
  "intro": "路旁倒著一名受傷的朝聖者，手裡緊握著一枚聖環徽章。",
  "options": [
    {
      "id": "heal", "label": "替他治療",
      "cost": { "items": [["藥草", 1]] },
      "outcomes": { "always": [{ "affinity_npc": 5 }, { "set_flag": "pilgrim_saved" }, { "offer_quest": "q_missing_pilgrims" }] }
    },
    {
      "id": "question", "label": "盤問他的來歷",
      "check": { "attr": "cha", "dc": 12 },
      "outcomes": {
        "success": [{ "set_flag": "learned_crypt_rumor" }],
        "fail": [{ "reputation": ["holy_ring", -1] }]
      }
    },
    { "id": "leave", "label": "離開", "outcomes": { "always": [] } }
  ]
}
```

**效果詞彙是封閉的**，程式只認得這些：`combat`（敵人組合，可帶受限的變體修正）、`item`、`money`、`hp`、`status`、`affinity_npc`、`reputation`、`set_flag`、`offer_quest`、`advance_quest`、`recruit_npc`、`reveal_location`、`time`。AI 寫不出程式不懂的東西，也就不會壞掉。

### 2.2 任務（Quest）：多地事件鍊＋旗標＋與旗標掛鉤的報酬

```jsonc
{
  "id": "q_missing_pilgrims",
  "title": "消失的朝聖者",
  "description": "索里耶爾的朝聖者接連在前往萊茵堡的路上失蹤……",   // 【任務描述】
  "rank": "E",
  "source": { "type": "tavern", "location": "soriel" },             // 或 npc / event
  "flags": {                                                         // 【旗標】
    "heard_rumor":     "在河谷鎮聽到失蹤者的去向",
    "found_camp":      "找到盜賊的藏身處",
    "rescued":         "救出朝聖者",
    "took_relic":      "私吞了聖環遺物",
    "spared_leader":   "放過盜賊首領"
  },
  "steps": [                                                         // 【事件鍊】
    { "id": "s1", "at": { "location": "rivervale", "place": "tavern" },
      "event": "ev_rumor_at_rivervale", "sets": ["heard_rumor"] },
    { "id": "s2", "at": { "location": "whisper_crypt", "layer": 1 }, "requires": ["heard_rumor"],
      "event": "ev_bandit_camp", "sets": ["found_camp"] },
    { "id": "s3", "at": { "location": "whisper_crypt", "layer": 2 }, "requires": ["found_camp"],
      "event": "ev_relic_choice", "sets_any": ["rescued", "took_relic", "spared_leader"] }
  ],
  "complete_when": { "any": ["rescued", "took_relic"] },
  "turn_in": { "location": "soriel", "place": "guild" },
  "rewards": [                                                       // 【與旗標掛鉤的報酬】
    { "when": { "all": ["rescued"] },               "money_cc": 600, "reputation": [["holy_ring", 3]] },
    { "when": { "all": ["took_relic"] },            "item": "聖環遺物", "reputation": [["holy_ring", -5]] },
    { "when": { "all": ["rescued", "spared_leader"] }, "affinity_npc": ["npc_selene", 5] }
  ],
  "expires_days": 20
}
```

旗標分兩層：**任務旗標**（只在這個任務內有效）與**世界旗標**（例如「救過朝聖者」，會影響之後的事件篩選與 NPC 態度）。報酬條件用 `all / any / none` 組合，程式負責求值。

### 2.3 實例化：模板 ≠ 進行中的任務

模板可以帶參數（`{town}`、`{npc}`、`{dungeon}`），接任務時程式把參數綁定到實際地點與角色，存成**任務實例**（模板 id＋綁定值＋旗標狀態＋已完成的步驟）。同一個模板因此可以重複使用，AI 生成的模板也能放進共用池。

## 3. 讓 AI 生成任務模板（需求 3）

流程：

```
玩家／開發者給一段文字
  → 程式組合提示詞：任務 DSL 說明＋可用詞彙（地點 id、場所、敵人、物品、效果、預算表）
  → AI 以結構化輸出回傳任務 JSON（模板＋其中引用的事件）
  → 程式驗證
       ├ 格式：符合 JSON Schema
       ├ 參照：地點、敵人、物品、狀態都存在
       ├ 可完成性：complete_when 至少有一條路徑可達；每個 requires 的旗標都有步驟會設定
       ├ 無死結：步驟之間沒有循環依賴
       └ 預算：報酬、敵人強度、檢定 DC 不超過該階級的上限
  → 有錯誤：把錯誤清單交回 AI 修正（最多 2 次）
  → 通過：顯示預覽（流程圖＋報酬表），由玩家確認採用
  → 存進任務池（存檔內，或匯出成 data/quests/*.json 與他人分享）
```

重點：

- **生成發生在「接任務前」，不是「遊玩中」。** 任務一旦被接受就固定下來，之後只執行，不再生成；這是穩定性的關鍵。
- **AI 可以發明的東西要分級**：
  - 自由發明：名稱、描述、NPC 名字與個性、台詞、物品的外觀描述。
  - 受限發明：敵人只能是既有敵人的**變體**（例如「首領」＝既有敵人 × 生命值 1.5、多一個能力、抗性調整在 ±0.5 內）；新物品若有效果，只能從既有效果類型中選、數值在預算內；沒有效果的劇情物品可以自由命名。
  - 不可發明：新的效果類型、新的傷害屬性、新的規則。
- 預算表放在資料裡（例如 E 級任務總報酬 30–160 銅、單一事件最多 1 場戰鬥＋1 場精英戰），AI 生成和程式驗證都看同一份。

## 4. 隨機事件（需求 4）

由程式的**事件導演**決定何時、何類，AI 只負責「換皮」：

| 場景 | 觸發時機 | 事件類型 |
|---|---|---|
| 地下城／荒野 | 走進格子時（或生成地圖時預先放置「特殊格」） | 特殊遭遇戰（有變體、有對話、有撤退條件）、特殊事件（壁畫、祭壇、受困冒險者）、特殊寶箱（擬態怪、陷阱、需要鑰匙） |
| 城鎮 | 走進特定設施格時 | 與場所掛鉤的邂逅：酒館的醉漢與情報販、神殿的懺悔者、市集的扒手、城門的難民 |
| 旅途期間 | 每段路程每天判定一次 | 遭遇戰（需要「中斷旅程 → 戰鬥 → 繼續」）、邂逅（商隊、巡邏隊、其他冒險者） |

導演的工作：

1. **機率與節奏**：每個場景的基礎機率、冷卻時間、最近事件的類型平衡（連續兩次戰鬥後提高非戰鬥事件的權重）。世界書「敘事傾向與事件觸發機制」的「引力值」也可以在這裡實作，作為可開關的節奏參數。
2. **篩選**：依場景、區域、時間、公會階級、世界旗標，從模板池挑出候選，按權重抽一個。
3. **綁定**：決定參與的 NPC、敵人組合、寶箱內容（都在預算內）。
4. **換皮（可選）**：把綁定好的事件交給 AI 寫開場描述與 NPC 台詞，不改變選項與後果。

模板池的來源有三：手寫、AI 離線批次生成並經過驗證、玩家用第 3 節的工具生成。建議**避免在遊玩當下即時生成整個事件**；即時生成延遲高、可能失敗、也比較難平衡。即時呼叫 AI 只用來換皮與敘事。

隨機事件也可以接上任務：事件的效果 `offer_quest` 就是需求 2 的「在某個地方遭遇突發事件後接取任務」。

## 5. 主角主動發起事件（需求 5）

> 更新：有了人際關係與共同記憶之後，建議改為「AI 預先寫好各種結果、程式擲骰決定走哪一條」，見 [`RELATIONSHIP_MEMORY.md`](RELATIONSHIP_MEMORY.md) 第 5 節。以下的動詞表方案保留作為 AI 關閉時的退路。

這是自由度最高、也最需要劃清權責的部分。原本建議用「**解讀 → 裁定 → 敘事**」三段式：

```
玩家輸入：「我把錢袋丟給守門的衛兵，請他當作沒看見我們。」
        │
 ① 解讀（AI）   程式提供：在場角色、可用動詞、玩家持有的物品與金錢
        │       AI 回傳：
        │       { "verb": "bribe", "target": "gate_guard", "approach": "cha",
        │         "offer": { "money_cc": 50 }, "argument": 0, "feasible": true }
        │
 ② 裁定（程式） DC = 目標基準 12
        │            + 實力差（角色扮演指導第一層）
        │            + 立場紅線：聖環教廷衛兵對賄賂 +4（第二層）
        │            − 出價相對於目標身分的價值
        │            + AI 給的論點品質（只允許 -2～+2）
        │       擲 1d20 + mod(魅力) + 熟練 → 部分失敗
        │       查後果表：bribe × 部分失敗 → 錢不收、起疑（旗標 guard_suspicious）、聖環聲望 -1
        │
 ③ 敘事（AI）   拿到完整結果後寫出衛兵的反應，不得與結果矛盾
```

設計要點：

- **動詞是封閉清單**：說服、威嚇、欺騙、賄賂、交易、贈禮、詢問、安撫、挑釁、示好、偷竊、潛行、攻擊……。每個動詞綁定預設屬性（說服＝魅力、威嚇＝力量或魅力、欺騙＝魅力、偷竊＝靈巧）與後果表。AI 只做「把自然語言對應到動詞與參數」，而這件事 AI 做得比任何規則都好。
- **AI 可以拒絕**：`feasible: false` 並說明原因（「你身上沒有 50 銀幣」「這裡沒有衛兵」），不會因為玩家寫得天花亂墜就憑空生出東西。物品與金錢只能是玩家實際持有的。
- **論點品質是有限加成**：玩家寫得有說服力，AI 可以給 +1～+2；明顯冒犯對方性格或立場則給 -1～-2。這讓「怎麼寫」有意義，但永遠不會壓過擲骰與實力差。
- **成敗分五級**：大成功／成功／部分成功／失敗／大失敗。後果表為每個「動詞 × 等級」列出候選後果（親密值變化範圍、聲望、旗標、是否轉入戰鬥），AI 可以從候選中挑一個最貼合情境的，但不能自創。
- **對象涵蓋**：
  - 夥伴：影響親密值（上限例如每次 ±8）、解鎖個人事件旗標。
  - 陌生人：可能產生新 NPC（名字與個性由 AI 生成，數值由程式依身分模板產生）、情報旗標、委託。
  - 談判對象：在戰鬥前或戰鬥中（花行動點）嘗試談判，成功可讓敵人撤退、投降或改變陣營。
  - 潛在敵人：挑釁、威嚇失敗可能直接轉入戰鬥，並給對方先攻優勢。
- **AI 關閉時的退路**：介面提供「動詞下拉選單＋目標＋出價」，跳過第 ① 步，直接進入裁定。這也代表主動行動系統可以先不靠 AI 做完並測好。
- 這個流程正好對應世界書「角色扮演指導」的四層判斷：實力差與立場紅線由程式計算，性格由 AI 判讀論點是否合乎對方性格，親密值由程式提供。

## 6. 穩定性清單

| 風險 | 對策 |
|---|---|
| AI 回傳格式錯誤 | 結構化輸出（JSON Schema）＋程式驗證＋最多 2 次自動修正＋預設退路 |
| AI 引用不存在的東西 | 提示詞只提供當下可用的詞彙子集；驗證參照完整性 |
| 數值失控、報酬膨脹 | 預算表、上限、AI 微調只在區間內 |
| 任務無法完成或卡死 | 生成時檢查可完成性與循環依賴；任務設期限，逾期自動失敗 |
| 同一件事重新生成結果不同 | AI 的每個決定存進存檔與報告；重新生成只換文字 |
| 玩家用文字「越獄」改規則 | 解讀階段只能選動詞與參數；規則與數值不在 AI 的輸出範圍內 |
| AI 拒絕或服務斷線 | 每個環節都有程式退路；遊戲在 AI 關閉時完整可玩 |
| 延遲與費用 | 任務生成用較強的模型、離線進行；解讀用較快的模型、輸入精簡；隨機事件以模板池為主 |

## 7. 建議的實作順序

1. **模板與執行時期（不接 AI）**：定稿事件與任務的 DSL 與 JSON Schema，實作旗標求值、任務實例、事件結算；手寫 2～3 條任務鍊與 15～20 個事件，確認 DSL 夠用。
2. **事件導演**：接上地下城／荒野的特殊格、城鎮設施的邂逅、旅途的中斷式遭遇。
3. **主動行動（先不接 AI）**：動詞清單、後果表、裁定流程，介面用下拉選單。
4. **接上 AI 解讀**：自由輸入 → 結構化意圖，論點品質加成。
5. **AI 任務生成工具**：文字 → 模板 → 驗證報告與預覽 → 採用／匯出。
6. **AI 換皮**：隨機事件與 NPC 的描述、台詞。

前 3 步完成時，系統已經完整、可測、不依賴 AI；之後每一步都只是讓 AI 去填既有的結構。

## 8. 待決定事項

1. **任務生成的時機**：只在「工具頁」由玩家手動生成並審核，還是也允許酒館在遊玩中即時生成（同樣經過驗證，但跳過人工預覽）？
2. **生成內容的歸屬**：AI 生成並採用的模板只存在該存檔，還是放進可匯出、可分享的共用池？
3. **主動行動的邊界**：哪些動詞開放？偷竊、暗殺、背叛隊友這類行為要不要開放？開放時後果要多重？
4. **主動行動的成本**：每次主動行動是否消耗時間（城內 10～30 分鐘）或行動點（戰鬥中）？是否限制同一對象的嘗試次數，避免反覆擲骰直到成功？
5. **NPC 的持久化**：主動行動與事件中由 AI 生成的陌生人，要不要登錄為正式 NPC（之後可以再遇到、可以招募）？
