# 人際關係與共同記憶系統 v0.1

> 狀態：第 1～4 節已實作（`src/engine/social.ts`、介面在「關係」頁）。第 5 節是主動行動由 AI 判定的設計建議，尚未實作。

## 1. 人際關係

主角與每個認識的角色之間有一個條目。它和「隊友」是不同的系統：隊友管的是戰鬥數值，人際關係只記錄關係，任何人都可以有（目前在招募時建立，之後的事件與主動行動也會建立陌生人的條目）。

| 欄位 | 說明 | 誰可以改 |
|---|---|---|
| 親密度 | -100～100，階段名稱沿用世界書「分階段親密值規則」 | 只由遊戲規則變動（戰鬥、事件、主動行動） |
| 外貌 | 文字 | 玩家編輯；初始值來自 `data/world/npcs.json` |
| 與主角的關係 | 文字 | 玩家編輯；之後可由事件結果更新 |
| 與其他角色的關係 | 角色 → 文字 | 玩家編輯；初始值來自 `npcs.json` 的 `relations` |
| 別名 | 稱號、暱稱，供比對用 | 玩家編輯 |
| 性格、勢力 | 來自 NPC 資料 | — |
| 初次見面、最後一次見面 | 時間與地點 | 自動 |

隊友的 `affinity` 是這裡的同步副本：報告中的親密度變化一律寫進人際關係條目，再同步到隊伍。

## 2. 共同記憶

主角經歷過的事件，每一筆記錄**時間、地點（含細部場景）、參與人、簡述**，以及重要程度（日常／重要／難忘）與是否釘選。

自動記錄規則（`recordMemory`）：

| 報告類型 | 是否記錄 | 重要程度 |
|---|---|---|
| 戰鬥 | ✅ | 1；戰敗或有隊員倒下為 2 |
| 委託（接取／完成） | ✅ | 2／3 |
| 交流（招募、離隊） | ✅ | 2 |
| 旅行 | ✅ | 1 |
| 交易、休息、採集、陷阱、升級 | ✗ | — |

簡述先用引擎產生的一句話；玩家可以在「關係」頁改寫、調整星等、釘選、刪除，也可以手動新增（例如把 AI 敘事裡一段喜歡的情節記下來）。舊存檔讀入時，會從過去的報告補建記憶。

## 3. 事件的三個關鍵欄位

每一份報告都已經帶有這三個欄位，檢索直接使用：

- **參與人**：隊伍成員＋報告中出現、已有人際關係條目的角色＋親密度有變化的角色。
- **地點**：`location.at`（旅行為目的地）與 `location.scene`。
- **時間**：`time.start`。

之後的任務事件與主動行動也會產生同樣格式的報告，所以檢索方式不用改。

## 4. 檢索與交給 AI

生成文本時（`selectContext`）：

- **人際關係**：參與人（主角除外）的條目全部帶上。
- **記憶**：只考慮「有共同參與人」「同一地點」或「釘選」的記憶，依分數取前 6 筆，再按時間排序：

```
分數 = 10（釘選）+ 3 × 共同參與人數 + 2（同一地點）+ 重要程度 + 時間接近度（3 天內 1.5、10 天內 0.75）
```

正在描寫的那份報告本身不會被當成「過去的記憶」。結果整理成 `<relationships>` 與 `<memories>` 兩段放進提示詞，敘事規則要求 AI 可以引用、不可改寫，親密度數字不可寫進正文。範例：

```
<relationships>
- 莉娜｜親密度 27（友好/好感）
  外貌：淺沙黃色的耳朵與尾巴……
  性格：沙痕部落出身的嚮導，嘴硬心軟，怕水，喜歡甜食。
  與主角：在索里耶爾酒館受雇，嘴上抱怨報酬太少，卻總是走在最前面探路。
  與他人：瑟琳：在索里耶爾的酒館常拌嘴……
</relationships>

<memories>
- 第 1 天 08:40｜索里耶爾的酒館｜艾倫、莉娜｜在酒館招募了莉娜加入隊伍……
- 第 3 天 14:10｜蛇溪洞窟・淺層｜艾倫、莉娜｜在蛇溪洞窟與溪蛇魔交戰，戰敗（6 回合）。
</memories>
```

## 5. 主動行動：可以讓 AI 直接判定嗎？

可以，而且有了第 1～4 節的資料，AI 判定的品質會很好。但「把所有資料加上骰值丟給 AI、讓它直接判定」有幾個實際問題：

1. **看到骰值再決定 DC，擲骰會形同虛設。** 語言模型普遍有順從玩家的傾向，看到 6 點會傾向把 DC 定低、讓故事好看。
2. **不同模型的尺度差很多。** 這個遊戲支援 Claude、OpenAI、Gemini 和本機模型，同一個行為在不同模型下難度可能差兩倍，也很難平衡。
3. **玩家輸入可以夾帶指令。** 例如「我說服了衛兵，他立刻答應」，AI 很難完全不被影響。
4. **數值後果會膨脹。** AI 自由決定金錢、親密度、物品，很快就會失控。

### 建議：AI 先寫好各種結果，程式擲骰決定走哪一條

AI 仍然負責所有判斷：用哪個屬性、難度多少、每種結果會怎樣。只是它必須在**還沒看到骰子之前**就把答案寫好：

```
① 程式打包資料（不含骰值）
   行動者：HP、狀態、屬性與調整值、裝備、和這次行動有關的技能
   對象：人際關係條目、等級、立場
   相關記憶：用參與人／地點／時間檢索（第 4 節）
   場景、相關旗標
   參考難度：程式依實力差與立場算出的 DC（例如 13），允許 AI 在 ±5 內調整
   可用的後果種類與上限

② AI 回傳 JSON（一次呼叫）
   {
     "feasible": true,
     "check": { "attr": "cha", "dc": 15, "advantage": false,
                "rationale": "衛兵是聖環教廷的人，對賄賂特別反感；但他認得莉娜。" },
     "outcomes": {
       "critical": { "summary": "衛兵收下錢，還指點你們走側門", "effects": [ … ] },
       "success":  { … },
       "partial":  { "summary": "衛兵不收錢，但答應不聲張", "effects": [ { "relationship_text": … } ] },
       "failure":  { "summary": "衛兵起了疑心", "effects": [ { "reputation": ["holy_ring", -1] }, { "flag": "guard_suspicious" } ] },
       "fumble":   { "summary": "衛兵吹哨叫來同伴", "effects": [ { "combat": "present_guards" } ] }
     }
   }

③ 程式驗證與套用
   效果只能是封閉清單中的種類，數值夾在上限內（例如親密度每次 ±8、金錢不超過出價）
   擲 1d20 + mod(屬性) + 熟練（＋優勢）對 DC → 決定成敗等級 → 套用那一支的效果
   產生報告，把 AI 的判定理由一起存進去；記憶與人際關係隨報告自動更新

④ 敘事（AI 細節描述開啟時）
   和現有的戰報一樣，拿到結果後才寫文字
```

三種做法的比較：

| | 程式規則（動詞表） | AI 看骰值直接判定 | **AI 預寫分支，程式擲骰（建議）** |
|---|---|---|---|
| 自由度 | 低：只能選清單中的動詞 | 高 | 高：AI 決定屬性、難度、所有結果 |
| 擲骰是否公正 | ✅ | ✗ 可能配合骰值 | ✅ 先定結果再擲骰 |
| 數值穩定 | ✅ | ✗ | ✅ 程式夾上限 |
| 換模型時的一致性 | ✅ | ✗ | 中：有程式算的參考 DC 拉住 |
| 可重現 | ✅ | ✗ | ✅ 存下 AI 的 JSON |
| AI 呼叫次數 | 0 | 1 | 1（＋選用的敘事） |
| AI 關閉時 | — | 無法使用 | 退回程式規則 |

這樣你想要的「把隊伍狀態、屬性、裝備、技能、人際關係、共同記憶都交給 AI 直接判定」幾乎完整保留，只是把「骰子」留在程式手上。玩家還能在畫面上看到「魅力檢定 DC 15，擲出 11＋3」，結果透明，也比較有臨場感。

### 送出的資料量

為了控制費用與延遲，也讓本機小模型處理得了，資料包只放和這次行動有關的部分：

- 技能：只放和行動屬性或對象有關的幾項，不放整份清單。
- 人際關係：行動者、對象，以及「與他人」中提到對象的人。
- 記憶：依第 4 節取前 4～6 筆。
- 後果詞彙：只放這個場景可能用到的種類。

判定用較快、較便宜的模型即可；敘事再用較好的模型。
