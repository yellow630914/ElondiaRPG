# AI 的上下文與工具調用（Agent 模式）計畫

> 上層：[ROADMAP](../ROADMAP.md) R29。狀態：**還沒開始**（2026-11-10 排入，先當測試性功能做）。
> 系統文件：[PROMPTS](../../PROMPTS.md)（敘事、判定的提示詞）、[ACTIONS](../../ACTIONS.md)（AI 判定）、[LEWD_STATS](../../LEWD_STATS.md) 第 29 節（性經歷記錄）、[TRAVEL_EVENTS](../../TRAVEL_EVENTS.md) 第 5 節（線索池）。
> 做完的部分寫回系統文件，從這裡刪掉，在[已完成](COMPLETED.md)記一段；玩家看得到的改動寫進 CHANGELOG 的「未發布」。

## 0. 起因（2026-11-10，Discord）

- 玩家在旅店長休，正文寫「有人塞了一封信」，約在某個地點見某個人。地圖上找不到那個地點和那個人；用主動行動去赴約時，下一則的人名又變了。
- 查過：遊戲沒有「睡覺時有人塞信」的內容，信、地點、人名都是寫正文的 AI 自己編的，存檔沒有記錄；判定的 AI 只看得到上一段正文最後約 300 字（前後銜接），人名沒傳過去，只好再編一個。
- 玩家的建議：城區地圖是固定的平面格子，可以轉成文字給寫正文的 AI，例如一行一行寫「商店 空地 通路 空地 酒館（NPC）」，讓 AI 知道這裡有什麼地方、誰在哪裡，寫出來的地點和人物至少找得到。**不是要 AI 生成地圖。**
- 擁有者的想法：之後試試看用工具調用（tool use）處理；成功的話，一些現在「另外送一次請求」或「在正文後面附一段 JSON 讓程式讀」的東西，也慢慢改成 Agent 模式，例如性經歷統計、報酬統計。

## 1. 先止血：不編接不上的鉤子（小）

和後面幾項無關，可以先做。

- 敘事規則（`DEFAULT_NARRATION_RULES` 的 hard_rules 第 1 條）與判定規則加一條：報告沒有的信件、邀約、約定見面、委託，以及新登場、有名有姓的人物和新地點，都不要寫進正文；可以寫氣氛、旁人、日常，但不要留需要玩家之後處理的事。
- 已經改過敘事規則的玩家不會自動套用（他們的規則照舊），要在 CHANGELOG 提醒可以按「恢復預設」或自己補一條。
- 順便處理點子庫 [I17](../ideas/player-feedback.md#i17)（日常小事不擲骰）的一半：日常小事的例子補上「讀信、看看自己身上的東西、整理行囊、回想」；沒有過程可言的事，骰值不影響經過。

## 2. 地圖與在場的人轉成文字給 AI（中）

玩家建議的做法。目前送給 AI 的地點資訊只有報告裡的地點名稱、`<bystanders>`（剛好在旁邊的人）與人際關係，AI 不知道這一區還有哪些地方。

- 新的區塊 `<here>`（後段，放在報告之前）：這一區的名稱、格子轉成的文字地圖，以及誰在哪一格。
  - 格式先試兩種，看哪種 AI 比較不會讀錯、字數比較少：
    1. **逐行文字地圖**（玩家的建議）：一行一列，格子寫地點名稱（商店、酒館、公會、通路、空地……），有人的格子後面括號寫名字；主角那一格標「（你）」。
    2. **地點清單**：只列有名字的格子與方位（「酒館：主角的東北方 3 格，老闆、2 位客人」），空地與通路不列。
  - 城外、地下城：地下城只列已經探索過的格子（不能洩漏沒看過的地方）；近郊與野外照同樣規則。
- 只在敘事、判定送；費用多幾百字。提示詞設定加一個開關（像「前後銜接」），預設開。
- 規則補一句：地點與人物只能用 `<here>`、`<relationships>`、`<bystanders>` 裡有的；要提到別的地方時用模糊的說法（「城東的某處」）。
- 要注意的：
  - 王宮、貴族區這類進不去的區域照樣列出名稱，但不列裡面的人。
  - 固定 NPC 的位置照「這裡的人」算（`peopleHere`），和畫面一致；只列名字與身分，不附任務資訊。
  - 存檔不用改。

## 3. 伏筆：讓 AI 合法地留下後續（中，先做 demo）

第 1 項把鉤子擋掉之後，如果想要 AI 偶爾留下「之後可以去找的事」，就讓它走程式驗證過的管道：

- AI 想留伏筆時，在正文後面另外輸出一段（和 `<relationship_updates>` 同一種方式）：誰、在哪裡、什麼時候、一句話說是什麼事。
  - **哪裡**只能填第 2 項 `<here>` 裡的地點（或這座城現有的地點 id）；**誰**只能填在場或認識的人的 id，或寫「新的居民」由程式產生（名字由程式決定，不讓 AI 自己取）。
- 程式檢查通過才採用：在那一格放一個事件點、記進冒險筆記（和線索、情報同一套：`intel.ts`、`leads.ts`），有期限，過期消失；檢查不過就丟掉，正文照舊。
- 玩家走到那一格時，那個人真的在那裡（臨時加進這一格的「這裡的人」）；之後的敘事與判定附上這則伏筆的內容，人名、地點就接得上。
- 限制：一座城同時最多一則；只在長休、酒館、打聽這類日誌允許；照內容篩選；固定 NPC 只能當見面的對象，不能動他們的劇情旗標。
- 存檔：新增一個選填欄位（例如 `state.hooks`），不用升存檔版本。
- 相關的點子：[I1](../ideas/early-design.md#i1)（AI 在事件中生成並登錄新 NPC）、[I2](../ideas/early-design.md#i2)（敘事輸出檢查），做這一項時一起看要不要併進來。
- 新地點：不生成地圖。真的需要「城外的廢屋、地下室」時，只能用線索事件的臨時地圖模板（`side_map`）。

## 4. Agent 模式：用工具調用取代事後解析（大，測試性）

現在 AI 和遊戲之間的資料交換有幾種做法，各自有問題：

| 現在的做法 | 例子 | 問題 |
|---|---|---|
| 另外送一次請求 | 性經歷記錄（`sexLog.ts`，正文寫完再請「性經歷記錄」的模型讀一次） | 多一次呼叫的費用與等待；會卡住（2026-11-10 補了逾時）；讀正文時可能和正文不一致 |
| 正文後面附一段讓程式讀 | `<relationship_updates>` | AI 不一定照格式；寫錯 id 就丟掉 |
| 判定回傳 JSON | effects（報酬、物品、親密度、入隊……）、findings | 一次要寫對整份 JSON；欄位越來越多，規則越來越長 |

Agent 模式：請求附上工具定義，AI 在寫作或判定的過程中呼叫工具，程式執行後把結果交回，AI 再繼續。

- **查詢的工具**（唯讀，取代把所有資料塞進提示詞）：這一區的地圖與在場的人（第 2 項）、某個人的人際關係與共同記憶、某個人的性經歷、主角的行囊與裝備、進行中的委託與特殊任務的公開狀態。
- **寫入的工具**（程式驗證後才生效，數值照現在的上限夾住）：
  - `record_sex`：性經歷記錄（取代另外一次請求）。
  - `grant_reward`：報酬、物品、金錢（取代判定 JSON 的 effects；「報酬統計」也從這裡記）。
  - `update_relationship`：關係描述與親密度（取代 `<relationship_updates>`）。
  - `add_hook`：第 3 項的伏筆。
- **原則**：
  - 工具只能做規則允許的事；不合法的呼叫回傳錯誤訊息讓 AI 改，不會直接失敗。
  - 一次請求的工具呼叫有次數上限（例如 6 次），超過就結束，用已經有的結果。
  - 每個功能各自一個開關（設定 → AI 敘事），預設關；關掉時照現在的做法，兩種要都能用。
  - 正文的串流不能被打斷：寫入類的工具最好在正文寫完之後呼叫，或先收集、正文結束後一次套用（回退日誌時一起回退，照 `snapshotState` 的做法）。
- **要先確認的**：
  - 各服務的工具調用支援：Anthropic、OpenAI、Gemini、Vertex 有原生的工具調用；`openai_compatible`（OpenRouter、本機模型……）不一定支援或格式不同，要能偵測、不支援時退回現在的做法。
  - 串流與工具調用一起用時，各服務回傳的格式（`providers.ts` 要多一個「有工具的對話迴圈」）。
  - 費用：工具結果會再送一次，查詢工具用多了不一定比現在便宜；要用快取（前段不變的部分）。
  - 和現有的 token 統計、AI 判定逾時、取消判定都要接上。
- **建議的試做順序**：先做一個查詢工具（第 2 項的地圖，看 AI 會不會主動查）＋一個寫入工具（`record_sex`，取代另外一次請求，效果最明顯），只開放 Anthropic 一家；確認穩定後再換掉 `<relationship_updates>` 與判定的 effects。

## 5. 順序

```
1 止血（規則一條）──→ 2 <here> 文字地圖 ──→ 3 伏筆（demo 先給擁有者確認）
                                    └──→ 4 Agent 模式試做（查詢地圖＋record_sex）──→ 逐步換掉其他事後解析
```

第 1 項隨時可以做；第 2 項做完，第 3、4 項都會用到它。
